# RCA — PersonalOS /admin "Admin access required" for mallireddymanikyalareddy@gmail.com

## Problem statement
Owner opens `/admin` on https://ai-personalos.emergent.host and sees "Admin access required. Your account doesn't have an admin role." Expected: `mallireddymanikyalareddy@gmail.com` should be `super_admin`.

## What was checked (production, read-only, active run 742c928b-26cd-4f59-8d41-41794f49eddf)

### 1. ADMIN_EMAILS secret — CORRECT ✅
`list_secrets` (active run) with expected-value comparison:
- `ADMIN_EMAILS` → `is_empty=false`, `matches_expected=true` for the exact string `mallireddymanikyalareddy@gmail.com` (no quotes/spaces, exact spelling).

So the env var is present and correct. This is NOT the problem.

### 2. users collection — THE ROOT CAUSE ✅ (proven)
`mongo_query` find on `users` (db `ai-personalos-personalos`), case-insensitive regex on email → exactly 1 match:
- handle: `mallireddy-manikyalareddy`
- stored email (exact case): `mallireddymanikyalareddy@gmail.com`  (lowercase, matches ADMIN_EMAILS exactly)
- **email_verified_at: `null`**  ← blocker
- admin_role: **absent** (field not present)
- admin_role_source: **absent** (field not present)
- created_at: `2026-10-26T17:17:18.78Z`

Per the described logic in `backend/admin.py`, both `promote_configured_admins()` (startup) and `ensure_admin_role()` (per request on GET /api/v1/admin/me) require the email to be in ADMIN_EMAILS **AND** `email_verified_at` to be non-null. The email matches, but `email_verified_at` is null — so super_admin is never granted. This fully explains the symptom.

### 3. Verification-email (Resend) logs — UNCONFIRMED
- `fetch_app_logs` on the active run and the two prior runs (68248e5c, 62312bab) returned **0 lines** over the max 1440-minute window. The signup/verification-email attempt happened on an earlier run's pods (user created 2026-10-26 17:17, during initial run 62312bab); those pods are gone and Loki has no retained lines, so I could not confirm or rule out a "Account email (verify) not sent" warning or a Resend send error.
- Observation from secrets: production env contains `EMERGENT_EMAIL_KEY` and `EMAIL_FROM_NAME` but **no dedicated `RESEND_API_KEY`**. If the verification-email send path requires a Resend API key under a name other than `EMERGENT_EMAIL_KEY`, that key is absent in prod and the email would never send — which would explain why `email_verified_at` is still null. This is INFERRED, not verified (the eph sandbox failed to extract source, so the send path's exact env-var name was not read).

## Conclusion
The account exists and the ADMIN_EMAILS secret is correct. The owner is denied admin solely because **`email_verified_at` is null** — the admin-promotion check gates on a verified email. The likely upstream reason is that the verification email was never completed/received (possibly never sent), which could not be confirmed from logs.

## Suggested fixes
1. **Immediate unblock (User, via DB Manager — read/write):** set `email_verified_at` to a timestamp on the user doc `id=cbf6ab92-334a-4711-92c4-06a3d0ba10c7`. On the next GET /api/v1/admin/me, `ensure_admin_role()` will promote them to super_admin (email already matches ADMIN_EMAILS). Alternatively restart triggers `promote_configured_admins()` at startup.
2. **User:** have the owner complete email verification via the link sent to that address (check spam / use the resend-verification flow) — this sets `email_verified_at` the normal way.
3. **Code (E1):** verify the verification-email send path and the env var it requires. Prod has `EMERGENT_EMAIL_KEY`/`EMAIL_FROM_NAME` but no `RESEND_API_KEY`; if the code sends via Resend using a differently-named key, the email never goes out and no user can self-verify. Optionally, consider bootstrapping configured ADMIN_EMAILS to super_admin without requiring email verification (or auto-verifying configured admins).
